### 1. `DeleteAccount` lacks OIDC guard
**File:** `src/Aiursoft.HowToCookViewer/Controllers/ManageController.cs:197`
The `DeleteAccount` GET/POST actions do **not** check if OIDC authentication is enabled. Every other sensitive action in `ManageController` (ChangePassword, ChangeNickname) guards with:

### 2. Double edge-resolution discrepancy in `LocalizeRecipesJob`
**File:** `src/Aiursoft.HowToCookViewer/Services/BackgroundJobs/LocalizeRecipesJob.cs`

The pagination cursor has switched from `!db.LocalizedRecipes.Any(...)` (which checked the full table each iteration) to `r.Id > currentLastId`:
```csharp
.Where(r => r.Id > currentLastId && !db.LocalizedRecipes.Any(lr =>
    lr.RecipeId == r.Id &&
```

This resolves the in-chunk ordering issue from the previous implementation. However, the `!db.LocalizedRecipes.Any(...)` subquery is **still evaluated for every recipe in the page** and translates to a correlated subquery in SQL. For large recipe tables, this is expensive. **Low severity.** Consider whether the `FileLastModified` comparison could be computed in a more efficient way (e.g., a join).

### 6. `DisjointSetUnion.AsGroups` readability

**File:** `Util/DisjointSetUnion.cs:18-43`

When `ignoreSingletons` is `false`, the root element of a group is included only when the iteration (which walks `[0, size)`) reaches `i == root` for that group's root. Since every root is in `[0, size)`, every root is eventually reached, and `Find(root) == root`, so `groups[root].Add(root)` executes. The tests confirm correctness — the code is just subtle enough to cause a double-take during review.

**Recommendation:** Add a brief comment explaining that in non-singleton-ignoring mode, root elements are naturally included when their own index is reached during iteration.

The rate limiter uses `IMemoryCache` — per-process, not shared across instances. For a single-instance deployment this is fine. For horizontal scaling, a distributed cache (Redis) would be needed. The class summary explicitly calls out "in memory," so this is documented behavior.

### `Embedding cache key` collision potential
`RecipeVectorSearchService.cs:172` truncates the query text to 40 characters for the database cache key (`text[..40]`). Two semantically different queries that share the first 40 characters (e.g., "chicken soup with carrots and celery sticks" vs. "chicken soup with carrots and leek slices") would share a cache key and return each other's embedding vector. In practice, cooking queries are typically short, and the impact is limited to re-ranking quality (not correctness), so the practical risk is negligible.
